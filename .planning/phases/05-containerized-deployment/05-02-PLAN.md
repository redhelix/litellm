<task type="auto">
  <name>Task 2: Verify DuckDB volume persistence across restart</name>
  <files>docker-compose.yaml</files>
  <action>
On docker-001, verify that the DuckDB named volume is mounted at the path the sidecar actually writes to, and that data survives a container stop/start.

**Step A — Find where sidecar writes metrics.duckdb:**
```bash
docker exec dashboard-sidecar find /data -name "*.duckdb" 2>/dev/null || \
docker exec dashboard-sidecar find /app -name "*.duckdb" 2>/dev/null || \
docker exec dashboard-sidecar env | grep -i duck
```

The volume mount in docker-compose.yaml is `dashboard-duckdb:/data`. The sidecar should be writing to `/data/metrics.duckdb`. If the file is found elsewhere (e.g., `/app/metrics.duckdb`), the volume mount path must be corrected in docker-compose.yaml.

**If path mismatch found:** Edit docker-compose.yaml dashboard-sidecar volumes to mount at the correct path (wherever the sidecar actually writes). Then re-deploy the sidecar:
```bash
docker compose stop dashboard-sidecar && docker compose rm -f dashboard-sidecar
docker compose up -d dashboard-sidecar
sleep 40
```

**Step B — Record current row count before restart:**
```bash
docker exec dashboard-sidecar python3 -c "
import duckdb
con = duckdb.connect('/data/metrics.duckdb')
tables = con.execute('SHOW TABLES').fetchall()
for t in tables:
    count = con.execute(f'SELECT COUNT(*) FROM {t[0]}').fetchone()[0]
    print(f'{t[0]}: {count} rows')
con.close()
"
```
Note the counts.

**Step C — Restart sidecar container:**
```bash
docker compose restart dashboard-sidecar
sleep 40
```

**Step D — Verify row counts are unchanged after restart:**
```bash
docker exec dashboard-sidecar python3 -c "
import duckdb
con = duckdb.connect('/data/metrics.duckdb')
tables = con.execute('SHOW TABLES').fetchall()
for t in tables:
    count = con.execute(f'SELECT COUNT(*) FROM {t[0]}').fetchone()[0]
    print(f'{t[0]}: {count} rows')
con.close()
"
```

Counts must be identical (or higher if new data arrived). If counts are zero after restart, the volume is not mounted at the right path — fix the docker-compose.yaml volume mapping.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| litellm-internal network | Only services that need db/proxy access are on this network; dashboard (nginx) is NOT on it |
| traefik-net | Dashboard (nginx) and sidecar are on this network for Traefik routing; db and redis are NOT |
| volume mount | DuckDB file is in a named volume — not bind-mounted to a host path accessible outside Docker |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-04 | Information Disclosure | DuckDB file accessible if volume bind-mounted to world-readable host path | accept | Named volume (not bind mount) — only container processes can read it |
| T-05-05 | Denial of Service | DuckDB grows unboundedly filling the named volume | accept | Low risk for lab — data volume is small; Phase 0 addresses spend log growth in Postgres |
| T-05-06 | Spoofing | Sidecar could be replaced with a malicious container on litellm-internal | accept | Local network only, no external exposure; lab threat model does not require container signing |
</threat_model>
